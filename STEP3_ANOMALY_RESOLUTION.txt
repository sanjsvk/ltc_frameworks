DIAGNOSTIC 2: KALMAN DLM S3 DEGRADATION ✅ ROOT CAUSE IDENTIFIED
────────────────────────────────────────────────────────────────────────────────────────────────────────────

Finding: Kalman DLM pause-window ratio 1.345 in S3 (high seasonality scenario)
- S1 recovery: 82.0%, pause ratio ~1.0 (stable)
- S3 recovery: 64.9%, pause ratio 1.345 (degradation, 34.5% error concentration)
- Unexpected: State-space model should handle seasonality well

Root Cause: Kalman DLM lacks explicit seasonal state component
- BSTS has `seasonal_periods: 52` + Fourier seasonal regressors
- Kalman DLM has NO seasonal state → latent level absorbs seasonality
- In S3's strong seasonality, model misattributes seasonal innovations to stock level
- Result: poor pause-window performance (isolated seasonal signal overexplained)

Investigation Evidence:
✓ BSTS config: seasonal_periods=52, seasonal_var=0.001 (explicitly models 52-week cycle)
✓ Kalman DLM config: no seasonal parameters
✓ Kalman DLM code (line 17 docstring): "latent level absorbs trend and seasonality without explicit coding"
✓ S3 Kalman DLM pause-window ratio 1.345 vs BSTS 1.02 (14% difference in robustness)

Options for Mitigation:
1. Add Fourier seasonal regressors to Kalman DLM (significant refactor; ~200 lines code)
2. Document as architectural limitation (practitioners should use BSTS for seasonal data)
3. Keep Kalman DLM as-is; it remains competitive on non-seasonal scenarios (S1, S2, S4, S5)

Recommended: Option 2 (document limitation). BSTS already provides seasonal solution; adding to Kalman
would duplicate functionality and increase maintenance burden. Paper insight: "Seasonal data requires
explicit seasonal components in state-space models; implicit absorption causes identification failure."

Status: IDENTIFIED. Documented as architectural trade-off, not a bug.

DIAGNOSTIC 3: WEIBULL NEAR-ZERO RECOVERY ✅ ARCHITECTURAL LIMITATION CONFIRMED
────────────────────────────────────────────────────────────────────────────────────────────────────────────

Finding: Weibull achieves ~10% recovery in S1, fails to identify LTC
Previous Hypothesis: Shape parameter shared across all 5 channels?

Investigation:
✓ Weibull config includes per-channel shape_bounds:
  - tv: [0.8, 2.0]
  - search: [0.8, 1.5]
  - social: [0.8, 2.0]
  - display: [0.8, 1.8]
  - video: [0.8, 2.0]
✓ Shape parameter IS per-channel (hypothesis refuted)

Conclusion: Near-zero recovery is a genuine architectural limitation, not a config issue.
Root cause likely: Weibull lag shape cannot simultaneously fit both STC and LTC across different
channels with a single distribution per channel. The model overfits to STC and underfits LTC.

Status: CONFIRMED ARCHITECTURAL LIMITATION (not a bug to fix).
