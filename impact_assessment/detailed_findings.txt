ISSUE #1: DualAdstockOLS Coefficient Index Misalignment (CRITICAL)
────────────────────────────────────────────────────────────────────────────────
File: /c/github/ltc/ltc/models/framework1/dual_adstock.py
Lines: 144-158 (decompose method)

Problem:
  In fit(), the code reserves space for missing channels by incrementing coef_idx
  WITHOUT adding coefficients to the regression matrix. In decompose(), this
  causes indices to be off when retrieving coefficients.

Code Snippet (decompose method):
  Line 144: coef_idx = 0
  Line 145: for ch in self._channels:
  Line 146:     col = f"{prefix}_{ch}"
  Line 147:     if col not in df.columns:
  Line 148:         stc_dict[ch] = pd.Series(0.0, index=index)
  Line 149:         ltc_dict[ch] = pd.Series(0.0, index=index)
  Line 150:         coef_idx += 2  # <-- BUG: increments for missing channel
  Line 151:         continue       # <-- but doesn't add to X_parts
  ...
  Line 156: stc_dict[ch] = pd.Series(self._coefs[coef_idx] * stc_ad, index=index)

Root Cause:
  Misalignment between X_parts dimensions (in fit()) and coef_idx iteration
  (in decompose()). Missing channels should either:
  (A) Be completely ignored (don't reserve space), OR
  (B) Have placeholder coefficients added to X_parts

Current behavior does neither: reserves space but adds nothing.

Impact on S1-S5:
  All 5 scenarios have all 5 channels present. Bug is inert for standard data.

Impact if channels missing:
  Example: If "search" missing, coef_idx jumps 0 → 2 (reserving 2 spots).
  But coefficients in self._coefs only have 8 values (4 channels × 2).
  decompose() tries to access self._coefs[2:4] expecting "social" coefficients,
  but gets "search" coefficients (wrong channel attribution).

S1 Recovery: 0.0% (published) — Not caused by this bug; architectural limitation.
Paper Impact: None (all channels present)

Fix Priority: LOW (not triggered by S1-S5 data)
Timeline: Post-publication refactoring

Fix Approach:
  Option 1 (Simple): Remove missing-channel handling entirely; assert all
           channels present during fit().
  Option 2 (Robust): Track actual coefficient indices separately from
           channel iteration order.

Example Fix:
  # In decompose(), maintain parallel tracking:
  coef_map = {}  # Map channel → coefficient index (only for present channels)
  coef_idx = 0
  for ch in self._channels:
      col = f"{prefix}_{ch}"
      if col in df.columns:
          coef_map[ch] = coef_idx
          coef_idx += 2
      else:
          coef_map[ch] = None

  # Then use:
  if coef_map[ch] is not None:
      stc_dict[ch] = pd.Series(self._coefs[coef_map[ch]] * stc_ad, index=index)

ISSUE #2: WeibullAdstockNLS Coefficient Index Misalignment (CRITICAL)
────────────────────────────────────────────────────────────────────────────────
File: /c/github/ltc/ltc/models/framework1/weibull_regression.py
Lines: 148-167 (decompose method)

Problem:
  decompose() uses enumerate(self._channels) to index into self._coefs,
  but self._coefs is indexed by feature_names order (which skips missing channels).
  Indices misalign if any channel is missing.

Code Snippet:
  Line 148: for i, ch in enumerate(self._channels):  # i = 0,1,2,3,4
  ...
  Line 158:     coef = self._coefs[i]  # <-- Uses enumerate index

  But in fit() (line 116-124):
    for ch in self._channels:
        col = f"{prefix}_{ch}"
        if col in df.columns:  # <-- Only adds if present
            ...
            feature_names.append(f"weibull_adstock_{ch}")

  So feature_names has only the present channels, but decompose() uses
  enumerate indices assuming all channels are present.

Root Cause:
  Off-by-one mapping between channel enumeration and coefficient array.
  Same root cause as Issue #1, but different code location.

Impact on S1-S5:
  All channels present → enumerate index matches feature array index.
  Bug is inert.

Impact if channels missing:
  If "search" missing (index 1 in enumerate):
    - enumerate: tv(0), search(1), social(2), display(3), video(4)
    - feature_names: tv(0), social(1), display(2), video(3), exog..., intercept
    - decompose() gets coef = self._coefs[1], expecting search, gets social
    - Wrong channel attribution

S1 Recovery: 10.5% (published) — Achieved despite bug (bug is inert).
Paper Impact: None (all channels present)

Fix Priority: LOW (not triggered by S1-S5 data)
Timeline: Post-publication refactoring

Fix Approach:
  Replace enumerate index with explicit feature_names lookup:

Example Fix:
  # In decompose(), change:
  for i, ch in enumerate(self._channels):
      if col not in df.columns:
          ...
          continue
      # OLD: coef = self._coefs[i]
      # NEW: Find coefficient index in feature_names
      feature_name = f"weibull_adstock_{ch}"
      if feature_name in self._feature_names:
          coef_idx = self._feature_names.index(feature_name)
          coef = self._coefs[coef_idx]
      else:
          coef = 0.0  # Channel not in features

────────────────────────────────────────────────────────────────────────────────

Lines: 205-213 (decompose method), possibly line 110 (fit method)

Problem:
  ARDLModel shows 0.0% recovery on S1 (published MAPE: 316.8%).
  This is a critical failure. The decompose() method is complex AR reconstruction.

  Paper note (CLAUDE.md):
    "ardl S1 failure was prior misspecification, not structural flaw"

  Suggests the bug is in configuration (wrong ltc_degree, wrong lags), not
  the decompose code itself.

Code Structure (inferred):
  decompose() reconstructs media contributions from AR coefficients:

  y[t] = β_0 + Σ(AR lags) y[t-i] + Σ(media terms) + Σ(exog terms)

  To isolate media contribution, must invert AR polynomial and solve for
  media effect. This is numerically complex and fragile.

Root Cause (hypothesis):
  Configuration issue: ltc_degree set to value that creates unstable AR lag
  structure (poles outside unit circle or close to 1).

  Example: If ltc_degree=3 and AR lags=[1,2,3], polynomial might be:
    φ(B) = 1 - φ₁B - φ₂B² - φ₃B³
  with roots close to unit circle → unstable.

  Decompose() AR inversion may use wrong lag count (ltc_degree vs actual AR order)
  causing shape mismatch or incorrect isolation.

  S1: ardl 0% recovery (CRITICAL)
  S2: ardl 68.8% recovery (WORKS)

  Why S2 works when S1 doesn't:
    - S2 has spend pause (weeks 104-112: TV & Video = 0)
    - This structural break may make AR easier to identify
    - Or, spend pause breaks collinearity that broke S1

  Suggests configuration is unstable, not code bug.

Paper Impact:
  HIGH. "ARDL shows critical failure on S1" is used as evidence that
  F2 < F3. If this is just a configuration issue, narrative is weakened.

  But S2 recovery (68.8%) is still mid-range, so overall ranking unchanged.

Fix Priority: HIGH (must understand before publication)
Timeline: Before publication (1-2 hour investigation)

Fix Approach:
  1. Check configuration: What are ltc_degree, stc_lags, exog_lags in S1 config?
  2. Try reduced ltc_degree (e.g., 2 instead of 3) and re-fit
  3. Check AR polynomial stability: Are any roots on unit circle?
  4. If ltc_degree is wrong: Fix and re-run S1
  5. If code bug: Check decompose() AR inversion logic

Diagnostic Steps:
  # In fit() or decompose():

  ar_coefs = [1.0] + [-coef for coef in ar_params]
  roots = np.roots(ar_coefs)
  max_abs_root = np.max(np.abs(roots))

      print(f"WARNING: AR polynomial unstable. Max root: {max_abs_root}")

ISSUE #6: FiniteDLModel Weibull Weight Dimension Mismatch (MEDIUM)
────────────────────────────────────────────────────────────────────────────────
File: /c/github/ltc/ltc/models/framework2/finite_dl_model.py
Lines: 122-126 (decompose or fit method)

Problem:
  Weibull weight array is generated with max_lag dimensions.
  But distributed lag structure uses ltc_degree effective lags.
  If max_lag ≠ ltc_degree, shapes don't match.

Code Pattern (inferred):
  w = weibull_cdf_weights(shape, scale, max_lag=52)  # 52 weights
  adstock = np.convolve(x, w, mode='same')  # Convolve with 52 weights

  But actual lag structure is polynomial of degree ltc_degree (e.g., 2).
  Polynomial degree 2 → effective lags ≈ 2, not 52.

  Result: 50 extra weights being applied, potentially padding with zeros
  or causing silent shape broadcast errors.

Root Cause:
  Confusion between max_lag (adstock window) and ltc_degree (polynomial order).
  For distributed lag with polynomial of degree d, effective lags ≈ d.
  But Weibull parameterization needs max_lag to define weight support.

Impact on S1-S5:
  S1: finite_dl 50.3% recovery (published)

  If weights are truncated to ltc_degree length: LTC underestimated
    → recovery drops to 40-45% (we see 50%, so maybe not this)

  If weights padded with zeros: Extra zeros added to convolution
    → Shape becomes (261 + 52) = 313, then trimmed back
    → Possible off-by-one error in time alignment

  If broadcasting silently fails: NumPy broadcasts (261,) and (52,)
    → Results in (261, 52) array of element-wise products
    → Sum collapses to scalar
    → No crash, but weights are wrong

  Published 50.3% suggests weights might be partially wrong (degraded recovery)
  but not completely broken.

Paper Impact:
  Medium. finite_dl is already documented as "mid-range" (50.3% recovery).
  If weights are subtly wrong, recovery might be 52-55% instead.
  Does not change F3 > F2 framework ranking.

Fix Priority: MEDIUM (investigate root cause)
Timeline: Before publication (quick verification)

Fix Approach:
  1. Check: Does FiniteDLModel use max_lag or ltc_degree for weight generation?
  2. Print weight array shape during fit()
  3. Verify: Weights are applied correctly in convolution
  4. Test: Compare finite_dl with explicit ltc_degree=52 vs ltc_degree=2
  5. If dimension mismatch: Align weight generation to use ltc_degree

Example Check:

  but the index algebra is error-prone. Off-by-one errors are common.

  No crash reported, so index arithmetic isn't catastrophically broken.

  Published 46.4% is mid-range, not great, suggesting model might be
